# New Tool Proposals — Reduce ExecuteCommand Usage

Date: 2026-09-06
Source data: `tmp/execute-command-groups.json`

## 1. Purpose

This document proposes new tools (and a small number of cross-cutting tool
changes) that would measurably reduce the agent's dependence on the
`ExecuteCommand` shell tool. Every proposal is grounded in an analysis of
`tmp/execute-command-groups.json`, which contains 4,686 recorded
`ExecuteCommand` calls (3,863 unique commands) collected from 17,927 response
sections.

Reducing raw shell usage matters because shell commands are the widest,
hardest-to-validate surface in the tool suite: quoting bugs, accidental file
mutation, output scraping, and sandbox escapes all concentrate there. Dedicated
tools replace free-form Bash with typed, validated operations that fail safely.

## 2. Key findings from the data

1. **Most calls are compound "shell plumbing", not real work.**
   - 2,500 of 4,686 calls (53%) start with `cd <dir> && ...` just to set a
     working directory.
   - 1,553 calls (33%) pipe through `head`/`tail` to truncate output.
   - 422 calls (9%) append `echo EXIT:$?` / `PIPESTATUS` to surface exit codes.
   - Combined, these patterns mean a large share of shell usage exists only to
     compensate for missing tool features (`cwd`, output limits, structured
     exit codes) that the runtime could provide directly.

2. **The `parameters` array is almost never used.**
   - Only 51 of 3,877 parameter-variant records passed a non-empty `parameters`
     array (~1.3%). Nearly all dynamic data is interpolated into the `command`
     string, which is exactly the injection-prone pattern `ExecuteCommand` was
     designed to avoid.

3. **A large share duplicates tools that already exist.**
   The most common effective command families (counting `cd ... &&` prefixed
   variants) are:

   | Effective command family | Approx. calls | Already covered by |
   | --- | ---: | --- |
   | `git ...` | ~1,060 | `Git` (partial — see §4.8) |
   | `grep ...` | ~740 | `Grep` |
   | `npm ...` (build/test scripts) | ~810 | none — **new tool** |
   | `ls ...` / `pwd` | ~450 | `ListDirectory` (+ small `Pwd` gap) |
   | `node ...` (`-e`, inline scripts) | ~195 | none — **new tool** |
   | `npx tsc` / `tsc` / local `tsc` | ~150 | none — **new tool** |
   | `cat ...` | ~140 | `Read` |
   | `echo ...` (markers) | ~145 | disappears with structured output |
   | `./agent-busctl ...` (mostly `--help`) | ~115 | `AgentBus` / `AgentBusEnrol` (+ `Help`) |
   | `go build/test/vet/version` | ~85 | none — **new tool** |
   | `rm` / `rm -rf` | ~73 | `Delete` / `Rmdir` |
   | `find ...` | ~70 | `Find` |
   | `sed ...` | ~72 | `Edit` (in-place edits) |
   | `stat` / `readlink` / `realpath` / `file` / `which` | ~50 | none — **new tool** |
   | `mkdir` / `rmdir` / `cp` / `mv` / `touch` / `chmod` / `ln` | ~35 | `Mkdir` / `Rmdir` (+ new `FileOps`) |
   | `env` / `printenv` / `whoami` / `id` / `ps` | ~25 | none — low priority |

4. **The most frequent single commands tell the same story.**

   | Calls | Command |
   | ---: | --- |
   | 107 | `pwd && ls -la` |
   | 40 | `git diff --check` |
   | 34 | `npm run build` |
   | 33 | `pwd` |
   | 24 | `cd <repo> && git diff --check` |
   | 15 | `pwd && ls` |
   | 12 | `cd <repo> && npm run build 2>&1 \| tail -30` |
   | 11 | `cd <repo> && git status` |
   | 9 | `npm run test:memory` |

5. **Git subcommands used via shell** (top-level `git` family): `-C` (124),
   `diff` (92), `status` (42), `log` (13), `rev-parse` (13), `check-ignore`
   (11), `show` (11), `add` (6), `worktree` (6), `ls-files` (5), plus smaller
   counts of `checkout`, `stash`, `restore`, `config`, `remote`, `branch`,
   `cat-file`, `clean`, `reset`, `rm`. Several of these are already supported
   by the `Git` tool but are still being shelled out to, so discoverability is
   part of the problem.

6. **`npm run` script concentration.** `build` (65), `test:tool-safety` (30),
   `test:tool-rendering` (14), `test:memory` (13), and a long tail of
   `test:*` scripts. These map cleanly onto a single package-script tool.

## 3. Cross-cutting changes (highest leverage, few or no new tools)

These are not new tools but multiply the value of every proposal below and
should ship first.

### 3.1 Add `cwd` to `ExecuteCommand` and all new process tools
A `cwd` parameter (already present on `Git`) would eliminate the 2,500
`cd <dir> && ...` prefixes. The process is spawned with `cwd` as the working
directory; `cwd` must resolve inside the workspace/safe-dir boundary.

### 3.2 Structured, bounded output with `durationMs`
`ExecuteCommand` already returns `exitCode`, `stdout`, and `stderr`, yet agents
append `; echo "EXIT:$?"` (422 calls) and `2>&1 | tail -N` (1,553 calls). Add:

- `durationMs` to the result.
- `maxOutputBytes` / `maxOutputLines` parameters (defaults matching the current
  1 MiB cap) so the model can ask for the tail it wants without a pipe.
- A rendered result that always shows `exit N` and elapsed time.

### 3.3 Promote and enforce the `parameters` array
Only ~1.3% of calls use `parameters`. Update the tool description and examples
to show `$1`/`$2` positional usage, and have the safety classifier strongly
prefer (or require) `parameters` whenever a command embeds path-like or
variable data. This single habit removes most shell-injection risk from the
remaining `ExecuteCommand` calls.

### 3.4 Redirect obvious duplicates to existing tools
Add a concise "use the dedicated tool instead" table to the `ExecuteCommand`
usage prompt and to the system tool list:

| Shell pattern | Use instead |
| --- | --- |
| `ls`, `pwd` | `ListDirectory` |
| `cat <file>` | `Read` |
| `find ...` | `Find` |
| `grep ...` | `Grep` |
| `mkdir` / `rmdir` | `Mkdir` / `Rmdir` |
| `rm <file>` | `Delete` |
| `git status/log/diff/ls-files/add/commit/worktree` | `Git` |
| `curl`/`wget` GET/POST | `Http` / `HttpRequest` |
| `agent-busctl ...` | `AgentBus` / `AgentBusEnrol` |

The classifier already refuses agent-bus and git-duplicate commands; extending
the deterministic duplicate detection to `ls`, `cat`, `find`, `grep`, `mkdir`,
`rmdir`, and single-file `rm` would mechanically recover a large share of the
4,686 calls.

## 4. Proposed new tools

### 4.1 `RunPackageScript` (highest priority)
Replaces ~810 calls (`npm run build`, `npm run test:*`, `npm run migrate:*`,
`npm --version`).

- **Purpose:** run a script declared in `package.json` without invoking a
  shell.
- **Parameters:**
  - `script` (string, required) — must exactly match a key in
    `package.json#scripts`.
  - `args` (string[]) — optional positional arguments appended after `--`.
  - `cwd` (string) — defaults to the workspace root; boundary-checked.
  - `timeoutSeconds` (number) — default 120.
  - `maxOutputBytes` / `maxOutputLines` (number) — optional.
  - `env` (string[]) — optional `KEY=value` overrides, passed literally.
- **Result:** `script`, `command` (argv), `exitCode`, `stdout`, `stderr`,
  `durationMs`.
- **Safety:** only `run <script>` is allowed — no `install`, `publish`,
  `exec`, `update`, or arbitrary npm subcommands. Script names are validated
  against the file, so an attacker-controlled `script` value cannot inject
  flags or extra commands. Runs under the existing shell sandbox policy.

### 4.2 `TypeCheck` (high priority)
Replaces ~150 calls (`npx tsc --noEmit ...`, `./node_modules/.bin/tsc`,
`node_modules/.bin/tsc`, bare `tsc`).

- **Purpose:** run the project's TypeScript compiler in check or emit mode.
- **Parameters:**
  - `files` (string[]) — files to compile; each must resolve inside the
    workspace.
  - `noEmit` (boolean) — default `true` (type-check only).
  - `outDir` (string) — optional; must resolve inside the workspace.
  - `tsconfig` (string) — optional path to a `tsconfig.json`.
  - `cwd` (string) — boundary-checked.
- **Result:** `exitCode`, `stdout`, `stderr`, `durationMs`, `files`.
- **Safety:** fixed, repo-approved compiler flags (es2022 / nodenext /
  skipLibCheck / node types) are applied by the tool rather than pasted by the
  model; flags are not user-extensible, preventing `--outDir /etc` or other
  flag-injection. Spawns `tsc` directly, never through a shell.

### 4.3 `GoToolchain` (high priority)
Replaces ~85 calls (`go build`, `go test`, `go vet`, `go version`, `gofmt`)
that today target the `agent-bus` Go repository and its worktrees.

- **Purpose:** run whitelisted Go toolchain commands for a Go module.
- **Parameters:**
  - `action` (string, required) — `build` | `test` | `vet` | `version` | `fmt`.
  - `packages` (string[]) — package patterns such as `./internal/ids/...`.
  - `race` (boolean) — append `-race` (test only).
  - `run` (string) — optional `-run` regex (test only).
  - `cwd` (string) — boundary-checked module directory.
  - `timeoutSeconds`, `maxOutputBytes`.
- **Result:** `exitCode`, `stdout`, `stderr`, `durationMs`, `action`.
- **Safety:** only the five actions are accepted; all other `go` verbs are
  refused. Package patterns are validated as safe argv (no `|`, `;`, or
  leading `-`). `fmt` is write-only-on-files and follows the
  `--allow-agent-source-modifications` policy; `version` is read-only.

### 4.4 `GetWorkingDirectory` (small but removes ~266 `pwd` calls)
- **Purpose:** return the current working directory and its symlink-resolved
  real path.
- **Parameters:** none (or `resolve` boolean, default `true`).
- **Result:** `cwd`, `realCwd`.
- **Rationale:** `pwd` was the 3rd most common single command (33 calls) and
  appears inside 107 `pwd && ls -la` calls. `ListDirectory` can also start
  returning its own `directory` + `realDirectory`, which covers most of the
  remaining need without a separate call.

### 4.5 `PathInfo` (small but high diagnostic value)
Replaces ~50 calls (`stat`, `readlink`, `realpath`, `file`, `which`,
`ls -ld`).

- **Purpose:** inspect filesystem metadata and resolve paths.
- **Parameters:**
  - `path` (string, required).
  - `action` (string) — `stat` | `lstat` | `realpath` | `readlink` |
    `which` | `type`.
- **Result:** `exists`, `type` (file/dir/symlink/other), `size`, `mode`,
  `mtime`, `symlinkTarget`, `resolvedPath`.
- **Safety:** read-only; refuses protected paths (`data.json`, credential
  stores, private keys) with the same policy as `Read`.

### 4.6 `FileHash` (small, supports the existing hash contract)
Replaces `node -e "...crypto.createHash('sha256')..."` one-liners.

- **Purpose:** compute a file digest.
- **Parameters:** `path` (string), `algorithm` (string, default `sha256`).
- **Result:** `algorithm`, `hash` (hex), `size`.
- **Safety:** read-only; protected-path policy applies. This makes the
  `read_hash` precondition for `Edit`/`Write`/`Delete` self-service instead of
  requiring an ad-hoc node script.

### 4.7 `FileOps` (one mutating tool with a strict action enum)
Replaces the long tail of `cp`, `mv`, `touch`, `chmod`, `ln` (and reinforces
the existing `Delete`/`Rmdir` split for `rm`).

- **Purpose:** perform simple, validated file operations without a shell.
- **Parameters:**
  - `action` (string, required) — `copy` | `move` | `touch` | `chmod` |
    `symlink`.
  - `source` / `destination` (copy, move, symlink).
  - `path` (touch, chmod).
  - `mode` (string, chmod only; validated octal or symbolic subset).
- **Safety:** every path goes through the same boundary and protected-path
  checks as `Write`/`Delete`. `move`/`copy` never follow symlinks for the
  destination directory. Mutating actions require
  `--allow-agent-source-modifications` or a declared `--safe-dir`.

### 4.8 Extend the existing `Git` tool (not a new tool, but a needed surface)
Replaces a large part of ~1,060 git calls that currently fall through to
`ExecuteCommand` because the `Git` tool lacks the subcommand.

- **Add read-only modes:** `show`, `rev-parse`, `check-ignore`, `branch`,
  `remote`, `config` (get only), `cat-file`, `clean --dry-run`.
- **Add safely-validated mutating actions:** `checkout`, `restore`, `stash`
  (push/pop/list), `branch` create/delete, `config` set (workspace-only).
- **Make `cwd` prominent** in examples; many shell calls were
  `git -C <dir> ...`, which is exactly `Git({ cwd: ... })`.
- **Keep the strict pattern:** each subcommand accepts only whitelisted
  parameters, never a free-form argument string, and path arguments pass the
  existing worktree/path policy.

### 4.9 `Help` (read-only tool/CLI help)
Replaces ~115 `./agent-busctl --help`, `./agent-busctl <cmd> --help`, and
`agent-busctl help <cmd>` calls.

- **Purpose:** return the usage documentation for an available tool or a
  supported external CLI.
- **Parameters:** `subject` (string) — a tool name (`AgentBus`,
  `AgentBusEnrol`, `Git`, `ExecuteCommand`, ...) or `agent-busctl` /
  `agent-busctl:<subcommand>`.
- **Result:** the matching `tools/*-usage.md` content (or a small built-in
  reference for external CLIs).
- **Safety:** read-only; never executes the CLI.

### 4.10 `RunScript` / `RunNodeTest` (optional, replaces most `node ...` calls)
Replaces ~195 `node ...` calls. This is intentionally split to avoid a general
eval tool where possible.

- **`RunNodeTest`** — runs `node --test <files...>` for workspace test files;
  parameters: `files` (string[]), `cwd`, `timeoutSeconds`, `maxOutputBytes`.
- **`RunScript`** — runs an existing `.js`/`.mjs` file in the workspace;
  parameters: `file`, `args` (string[]), `cwd`, `timeoutSeconds`,
  `maxOutputBytes`.
- **`NodeEval`** (last resort, gated) — evaluates a supplied JavaScript
  snippet for smoke checks and assertions, in the sandbox with no network, a
  private temp dir, protected-path read/write denial, a hard timeout, and an
  output cap. This should be gated behind
  `--allow-agent-source-modifications` and the deterministic safety
  classifier, and the prompt should steer agents to `RunScript`/`RunNodeTest`
  first.

## 5. Prioritized rollout

| Phase | Items | Why first |
| --- | --- | --- |
| 0 | §3 cross-cutting changes (cwd, output limits, `parameters`, duplicate redirection) | Highest leverage; recovers most duplicate usage with no new tool code |
| 1 | `RunPackageScript`, `TypeCheck`, `GoToolchain` | Removes the build/test/typecheck core (~1,050 calls) that has no existing tool |
| 2 | `GetWorkingDirectory` + `ListDirectory` enrichment, `PathInfo`, `FileHash` | Small, safe, read-only tools that remove common diagnostics |
| 3 | `FileOps`, `Git` subcommand expansion, `Help` | Removes mutating shell one-offs and git/CLI-help fall-through |
| 4 | `RunScript` / `RunNodeTest` / gated `NodeEval` | Replaces inline node evaluation with sandboxed, bounded execution |

## 6. Expected reduction

A conservative estimate, counting a call as "removed" when a proposal provides
a direct replacement:

- Phase 0 alone redirects roughly 2,200–2,600 calls to existing tools
  (`ls`/`pwd`/`cat`/`find`/`grep`/basic `git`/`mkdir`/`rmdir`/single-file
  `rm`/`curl`/agent-bus) and removes the shell plumbing around the rest.
- Phases 1–3 add ~1,300 further replacements (`npm`, `go`, `tsc`, file
  metadata, file ops, git subcommands, help).
- The remaining `ExecuteCommand` usage should be genuinely ad-hoc shell
  verification (compound diagnostics, one-off checks) — on the order of
  **700–1,100 calls out of the original 4,686, a ~75–85% reduction**.

These are planning estimates, not guarantees; each phase should re-run the
same grouping analysis against a fresh log to confirm the reduction.

## 7. Risks and mitigations

- **Tool sprawl.** Mitigate by grouping small operations (`FileOps`,
  `PathInfo`) and keeping each new tool's action set strict and enumerable.
- **Eval risk from `NodeEval`.** Keep it gated, sandboxed, read-only outside a
  scratch dir, and prefer `RunScript`/`RunNodeTest`. If the risk is
  unacceptable, drop `NodeEval`; the other proposals still deliver most of the
  reduction.
- **Flag/option injection in new process tools.** Every new process tool
  spawns directly (no shell), builds argv from typed parameters, validates
  enum values, and rejects leading `-` in path/package arguments.
- **Sandbox compatibility.** New process tools must reuse the existing
  `AGENT_SHELL_MODE` sandbox/trusted-host policy and its 120-second,
  1 MiB-output defaults so they fail identically to `ExecuteCommand` today.
- **Regressions in discoverability.** Ship the §3.4 mapping table in the same
  change as any new tool, and update each tool's `tools/*-usage.md`.

## 8. Success metrics

1. `ExecuteCommand` call count per response section drops by ≥50% after
   Phase 0 and ≥75% after Phase 3.
2. `parameters` usage rises from ~1.3% to >80% for the remaining
   `ExecuteCommand` calls.
3. `cd ... &&` prefixes fall below 5% of `ExecuteCommand` calls.
4. `2>&1 | tail/head` and `echo EXIT` patterns fall below 2% of
   `ExecuteCommand` calls.
5. Zero new tools accept free-form shell strings; every new tool is
   argv-based and path-boundary-checked.
